# Plan: `build-guidance` plugin

> Superseded by the 3-plugin consolidation of 2026-08-22 (see `docs/architecture.md`); paths and
> plugin names here are historical.

Status: **implemented 2026-08-16** (all four phases; see commits b840e58…). Notes on deviations at the end. Originally authored 2026-08-16 in a planning session of the sister project
(`ai-security-framework-viz`); build this in a session in THIS repo.

## Why

The sister project `ai-security-framework-viz` is **for architects**: risk maps down to reference
architectures, plus (in progress) per-architecture controls guidance for admins/security teams
(managed settings, MDM, gateways, allowlists). This repo is **for developers**. The missing
developer-facing piece is the rung below a reference architecture: *how do I set up my environment
securely, and what do I start building from?* That is this plugin.

Two jobs:

1. **Environment setup** — configure your AI coding/agent tools securely (permissions, sandboxing,
   egress, MCP client trust), as an individual developer. The admin-side enforcement of the same
   surfaces lives in the viz project; this plugin covers what the developer controls.
2. **Secure-by-design starters** — architecture-aware scaffolding templates with TODOs that a team
   picks up instead of building from scratch, then hardens under the existing `secure-plan` flow.

## Non-duplication contract

- **CodeGuard / `secure-plan`** answers "what rules apply while I build." `build-guidance` answers
  "what do I start from and how is my environment configured." A starter template is the paved-road
  starting point; the Compliant Build Plan still governs everything built on top. Every template
  TODO cites the control family it implements using the vocabulary already in
  `plugins/secure-plan/skills/compliant-build-plan/references/ai-controls.md`, and both skills end
  by handing off to `secure-plan` (security profile + CBP).
- **`asset-scan`** owns vetting MCP servers and skills before trusting them. The `agent-setup`
  guides link to it at the admission step; nothing is reimplemented.
- The viz project owns the reference-architecture catalogue. This plugin carries a *distilled*
  snapshot (see `architectures.md` below) with provenance, not a fork of it.

## Plugin shape

Eighth plugin, phase **Plan/Code** (alongside `secure-plan`). Follows every repo convention:

- `plugins/build-guidance/plugin.json` — Agent Plugins 1.0 spec, source of truth (match
  `secure-plan/plugin.json`: `$schema`, name `ai-security-build-guidance`, MIT, author block).
- Client manifests generated by `scripts/sync_manifests.py`; validate with `scripts/validate.sh`
  and `scripts/check_spec.py`.
- Rows in `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json`; README table
  row; `docs/architecture.md` section.
- Skills: `SKILL.md` with YAML frontmatter incl. `compatibility:` network-access declaration
  (the structured field Cisco skill-scanner checks — see `docs/security-evaluations.md`).
- No MCP servers needed; no scripts initially.

```
plugins/build-guidance/
  plugin.json
  skills/
    agent-setup/
      SKILL.md
      references/guides/
        claude-code.md
        codex.md            # covers CLI + VS Code extension in one guide
        cursor.md
        github-copilot.md
        personal-agents.md  # OpenClaw-class daemons: hardened-runtime position
    secure-starter/
      SKILL.md
      references/architectures.md
      references/templates/<archetype>/...
```

## Skill 1: `agent-setup`

Developer-side secure setup of AI coding/agent environments.

**Flow (SKILL.md):** detect which tools are present (config dirs, lockfiles, `which`) → walk the
relevant guide(s) → verify the resulting configuration (read back the settings files, list active
MCP servers) → summarize residual risk and hand off MCP/skill vetting to `asset-scan`.

**Guides** (`references/guides/<tool>.md`), one per tool, each covering the developer-controlled
surfaces:

- permission/approval configuration (allowlists, deny rules, approval modes)
- sandboxing (built-in sandbox modes; container/devcontainer patterns where the tool lacks one)
- network egress (proxy settings, domain allowlists where supported)
- dotfile/config hygiene (what arrives with a cloned repo and gets auto-trusted; project-level
  config the developer should review before first run)
- MCP client trust: server admission, OAuth scoping, per-server permissions → `asset-scan` hand-off
- secrets hygiene (env files, credential helpers, what the agent can read)

`personal-agents.md` is the odd one out: an explicit, opinionated position on running
OpenClaw-class always-on personal agents — bare host install vs Docker Sandboxes
(no-network default, read-only root, dropped capabilities) vs more locked-down variants
(evaluate "Hermes"-class runtimes at authoring time), with a recommended default.

**Fact discipline:** every vendor-specific path, key, or precedence claim carries an `asOf` date
and a source URL, verified against the live vendor doc at authoring time — never recalled. The viz
project's tool research (its `data/reference/guidance/tools.yaml`) can seed the admin-adjacent
facts, but developer-surface facts need their own verification pass.

## Skill 2: `secure-starter`

Architecture-aware scaffolding.

**Flow (SKILL.md):** developer describes what they're building → map it to a reference architecture
via `references/architectures.md` → confirm the match with the developer → copy
`references/templates/<archetype>/` into the project → walk the TODOs → record what was applied →
hand off to `secure-plan` for profile + CBP.

**`references/architectures.md`:** distilled catalogue of the viz project's reference
architectures — id, one-line summary, the key pinned capabilities (the security requirements the
architecture carries), and "choose this when" discriminators. Provenance header pointing at the viz
repo and the date of the snapshot. Regenerate manually when the catalogue shifts; note that the viz
catalogue is itself under active revision (the hosted agent workflow archetype in particular), so
snapshot at build time.

**Templates are scaffolding with TODOs, not runnable apps:**

- Each file is a skeleton: real structure, stub implementations, `# TODO(control-family):` markers
  citing `ai-controls.md` families (e.g. `tool-least-privilege`, `egress`, `logging-audit`).
- Auth is always a documented stub — it differs per org; the template documents the integration
  points at pattern level.
- Modular: compose services / modules are pick-and-choose, and the SKILL.md says which are core
  vs optional.

**First template — hosted agent workflow** (`references/templates/agent-workflow/`):
docker-compose + LangGraph/LangChain skeleton (verify current versions at authoring time):

- orchestrator service (LangGraph app skeleton, typed tool registry)
- tool gateway / allowlist stub (single egress point for tool calls)
- compose networking with default-deny egress between services; internal-only networks
- sandboxed executor service (isolated container for code/command execution)
- audit-log sink (structured tool-call logging)
- hardened compose defaults: `no-new-privileges`, `read_only` where possible, dropped caps,
  pinned image digests — each with a TODO explaining what to keep
- auth TODO stubs at the boundary

Later templates: RAG assistant, remote MCP server (both already have viz-side architectures).

**Shared state:** reads `.ai-security/profile.md` if present; writes `.ai-security/starter.md`
recording template id + version applied, so `secure-plan`/`remediate` see provenance.

## Phasing

1. **Scaffold** — plugin.json, empty skills, manifests synced, validate.sh green, marketplace/README
   /architecture.md rows. (Small PR.)
2. **`agent-setup`** — SKILL.md + the four coding-tool guides + `personal-agents.md`. Research pass
   against live vendor docs; date everything.
3. **`secure-starter`** — SKILL.md + `architectures.md` snapshot + the agent-workflow template.
4. **More templates/guides** — RAG assistant, remote MCP server; additional tools as demanded.

## Verification

- `scripts/validate.sh` passes (spec schema, manifest sync, skill frontmatter).
- Dogfood `agent-setup` on this machine's own Claude Code/Cursor setup; confirm the guide's
  verification steps read back real config.
- Dogfood `secure-starter`: scaffold the agent-workflow template into a scratch dir; compose
  config parses (`docker compose config`); TODO markers enumerable via grep; hand-off to
  `secure-plan` produces a CBP that references the template's stated control families.

  `secure-build-plan` (SBP). The new skills hand off to `security-profile` → `secure-build-plan`.

  Codex guides' Verify blocks read back real config on this machine; Cursor/Copilot could not be
